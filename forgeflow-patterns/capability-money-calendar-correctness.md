# Money and calendar correctness

Status: evaluation cohort, version 1. Select when currency representation, allocation, conversion, recurrence or calendar arithmetic changes. A financial project name, copy edit or unrelated UI change alone is insufficient. Normal automatic execution awaits benefit qualification. Use the application's existing domain model and test seam; this procedure is not a replacement ledger or a source of accounting policy.

## Establish the product contract

Trace entry, parsing, stored representation, computation, preview, commit, import/export and presentation. Reuse change propagation for shared units/schema consumers and persistence recovery for interrupted or concurrent writes. Record the unit and currency at every boundary, minor-unit exponent, supported magnitude, precision, sign rules, rounding mode and stage, allocation remainder rule, and provenance of missing values. Do not assume all currencies use two decimal places or silently perform exchange conversion.

Separate a civil date, a year-month and a timestamp. Record supported years, calendar, date parsing grammar, recurrence anchor, interval, inclusivity, timezone and handling of unavailable dates. Distinguish an original day-of-month anchor from the previously emitted date; explicit end-of-month behavior is a different valid policy. Specify whether a missing occurrence is clamped, skipped or rejected and how leap-day anniversaries work. For timestamp-based schedules, establish daylight-saving gap/fold policy and whether duration means elapsed hours or civil days. Do not impose a timezone on civil-date-only data.

Use existing tests and documented policy first. If policy is genuinely unspecified, state the competing outcomes and resolve the product question before declaring one a defect. Never infer financial/legal requirements or a locale's rounding policy from a formatter. Keep fixtures synthetic; selecting this capability does not authorize reading real accounts, migrations, live payments or destructive tests.

## Derive invariants and adversarial examples

- **Representation and bounds:** convert exact decimal input at the declared boundary, with explicit units. Reject malformed, non-finite, out-of-range or unsupported future data without writes. Verify cents-versus-major-unit changes across storage, imports, exports, totals and display. Check boundaries before and after arithmetic; intermediate overflow or binary floating-point rounding can invalidate an otherwise in-range result. Use the application's established integer/decimal implementation, not a new parallel calculator.
- **Rounding:** test values immediately below, at and above positive and negative ties. Distinguish half-even, half-away and other documented policies; specify whether rounding occurs per line, per conversion or only at an aggregate. Legitimate differences between policies are not errors. Include refunds, negative zero and precision/exponent changes. Freeze expected values independently of the code under test.
- **Conservation:** allocations sum exactly to their input, transfers preserve a declared total absent named fees, and inverse/round-trip conversions preserve values where the contract promises it. Check remainder allocation, sign, empty inputs, missing amounts, cross-currency/unit rejection and bounds. Aggregate-then-round and round-then-aggregate need not agree unless policy requires it.
- **Recurrence:** exercise days 28–31 across short months, February 29, non-leap centuries, leap centuries, December/January, interval multiples and lower/upper supported years. Recompute each occurrence from the original anchor. A January 31 → February 28 clamp must not silently become a permanent day-28 anchor. Test intentional end-of-month and skip policies as clean controls. Repeated previews must be stable; bounded enumeration must stop or report a range error rather than loop indefinitely.
- **Missing data and no-write behavior:** distinguish absent/null/unentered from an explicit zero and from stale or invalid data. A partial known subtotal must not appear as a complete total. Snapshot stored bytes and write/remove events before previews, validation failures, unsupported dates and read-only reports. Check that defaults, normalization, migration or caching do not persist merely because a view was opened. Assert failure preserves bytes, and valid commits perform only the expected write. Pure calculation tests alone cannot establish the application's storage boundary.

Start with literal defect and clean examples, then a bounded deterministic set of generated cases with a saved seed and range. Use an independent oracle or metamorphic property; deriving expected output through the same implementation only confirms agreement with itself. Add deliberate mutations for the changed mechanism so a clean harness that never exercises the bad path cannot pass unnoticed. Application-specific cases should exercise the real entry point and consumers, not just a model rewritten to pass the tests.

## Verify presentation and report the evidence

Formatting is a presentation boundary. Keep canonical numeric/date storage independent of grouping separators, decimal marks, currency symbols and localized month/day order. Test explicit supported locales, negative and zero values, large/long output and readable missing/error labels; do not feed formatted strings back into a canonical parser. Compare format parts or declared locale output while acknowledging runtime locale data. For civil dates, test under multiple process timezones to catch accidental UTC/local conversion; timestamp schedules additionally need actual timezone/DST tests. A civil-date fixture does not qualify those timestamp semantics.

Where UI changes, check keyboard editing, focus/error association, readable totals and missing states, text enlargement and narrow reflow using visual acceptance. Passing arithmetic or locale-string tests is not an accessibility observation.

Return source identity, exact commands, policies, unit/date flow, fixed cases, generated seed/ranges, detected mutations, stored bytes/write events, observed locale/timezone behavior and remaining gaps. Preserve expected and actual results separately. Stop after scoped invariants pass or a concrete missing policy/tool is documented; clean up only owned disposable data after retaining sanitized evidence.

The checkout's `node scripts/forgeflow/test-money-calendar-correctness.js` exercises an authored model with exact integer intermediates, explicit rounding and civil-date policies. Its README declares ranges and omissions. These are implementation checks, not proof of application correctness or model benefit. Future benefit comparisons should use pinned real-project changes, equal baseline/enhanced access and independent verification, preserving ties and regressions as well as gains.
