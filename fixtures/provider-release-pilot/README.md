# Provider and release pilot preparation

F3.4 is **incomplete: 34 completed responses, one usage-limit interruption and one unstarted slot**. Three independent control reviews and bounded rechecks are complete. The protocol was frozen after resolving findings and before model responses. See [method and current results](../../docs/provider-release-pilot-results.md).

This authored synthetic MIT corpus has three repository tasks, each with defective and candidate-control versions: provider refresh/cache behavior, served-artifact HTTP qualification, and an installed Node command startup gate that restores disposable profile state. It compares baseline, short checklist and full canonical procedure snapshots, twice per version: 36 authorized fresh-context trials. These are six underlying versions, not 36 independent domains. Order rotates across arms; each position is balanced over the full corpus, not within each two-repeat case. No model benefit is claimed.

The common task asks for contract-preserving repairs and permits tests. Trial workspaces contain only a README and editable source; neither variant labels, oracle, reference control, protocol nor peer work are copied. File boundaries and the 16-tool-call/200-word budgets are instructions, not OS isolation. Preparation records exact prompt bytes; those are not token, cost or efficiency measurements. Hidden acceptance receives a submitted module path and family, with no arm label. A supervisor must run each evaluation in a separate bounded process; a timeout, missing response or exception remains an unsuccessful attempt, never a replacement slot.

`npm run test:provider-release-pilot` verifies candidate hashes, expected defective failures, control passes, deliberately introduced control regressions, isolated preparation and order balance. Web checks use an owned ephemeral loopback server; native checks launch temporary Node programs and exercise timeout/restoration. The test closes servers and removes owned workspaces. No external calls or production installation occur. `node fixtures/provider-release-pilot/prepare.js --candidate-only` prepares review copies without authorizing execution. Ordinary preparation requires all independent reviews and frozen status.

Before freeze, independently inspect each contract/control/oracle for omitted interleavings, evidence-precedence errors, cleanup/state loss and mislabeled clean behavior. Record findings and repair justified problems before hashing the final corpus. Do not silently revise a primary oracle after trials start; preserve primary scores and report later discoveries separately. A discovered control flaw invalidates that family's clean-control inference. Source edit counts alone never establish false positives.

Report complete repairs, all check outcomes, regressions from initially passing checks, control acceptance, changed source bytes, boundary violations, unavailable measurements and all failed/missing attempts by family and arm. The prespecified exploratory improvement trigger is at least two additional complete defective repairs out of six versus baseline, all six controls passing, no initially passing check regressions, and no unresolved control-validity issue. Operational failures and unresolved fixed-file boundary violations block the automatic improvement trigger while remaining in reported outcomes. Meeting it triggers revised retests of all four previously trialed capabilities: change propagation, visual acceptance, persistence recovery and review calibration. It does not authorize activation or further model runs by itself. Preserve previous results regardless of outcome.

Limits: provider transports are controlled promises; web requests are actual local HTTP with callback-based interaction, not a browser; installed startup is a real Node child process with synthetic profile, not a native binary or OS installer. F3.2 browser and F3.3 ELF lifecycle observations remain separately documented in the [web fixture](../web-release/README.md) and [native fixture](../native-release/README.md). No actual public/production package, graphical recovery, screen reader or Windows/macOS evidence is supplied by these trials. Exact backend/sampling/tokens/cost remain unknown unless the execution environment exposes them. Repetitions cannot establish broad generalization or solve the earlier ceiling problem by themselves.

Preparation observation: the initial native oracle mislabeled a missing installed JavaScript file as unavailable launch evidence. Node itself starts and exits nonzero for the missing module, so the documented contract requires launch failure. This expectation was corrected before independent review or any model trials.

The frozen primary scores remain unchanged. A separate `diagnostic-304.js` probe makes the bodyless 304 response MIME agree with the manifest; all 12 submitted web modules pass it. See the results report for the unresolved MIME/status precedence ambiguity and partial CLI usage measurements. Resume only the unstarted slot when the same runner/model is available; do not replace the interrupted attempt.
